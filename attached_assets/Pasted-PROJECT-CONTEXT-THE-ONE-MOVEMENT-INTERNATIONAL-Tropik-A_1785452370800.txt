ARCHITECTURE PRINCIPLES (enterprise-grade, portability-first — enforce all)
- Identity is decoupled from credentials: the users table holds identity; a SEPARATE credentials concept holds the password hash. This is what lets SSO/OAuth/enterprise providers attach later as ADDITIONAL identity sources without touching identity or sessions.
- Sessions are opaque, server-side, revocable. NO JWT carrying authorization. A session references a user; capabilities are looked up per-request server-side (capability system arrives in Module 2.3 — for now a session simply authenticates identity).
- Password hashing: argon2id (preferred; if argon2 unavailable in this environment, use bcrypt with cost ≥ 12 and document the choice). NEVER store or log plaintext or hashes anywhere but the credentials store.
- All auth secrets from Replit Secrets. Nothing in code.

PART D — SCHEMA (additive; new tables only; do NOT alter existing users columns unless a strictly additive nullable column is required, and if so report it)
Create via Drizzle + a generated migration (NOT push):
- user_credentials: id · user_id (FK users, unique — one credential row per user for password auth) · password_hash (text, never null for password users) · hash_algorithm (text — e.g. "argon2id") · password_updated_at · created_at · updated_at. (Separate table = future SSO users can exist with NO credential row.)
- sessions: id (opaque random, sufficiently long, unique — this is the session token stored in the cookie; store a HASH of the token, not the raw token, so a DB leak doesn't expose live sessions) · user_id (FK users) · created_at · expires_at · last_seen_at · revoked_at (nullable) · user_agent (text, optional) · ip_created (text, for security audit only). 
- auth_events (security audit log — append-only): id · user_id (nullable — failed logins may have no valid user) · event_type (enum: register | login_success | login_failure | logout | session_revoked) · created_at · ip · user_agent. Do NOT log emails or tokens here — user_id + event only.
Generate the migration, review the SQL (must be pure additive CREATE TABLE / constraints / indexes — zero destructive statements; if destructive, STOP and report), apply via migrate. Report filename + full SQL. Add a unique index on sessions token-hash and on user_credentials.user_id.

PART E — EMAIL/IDENTITY NORMALIZATION
Reuse the platform convention: emails normalized to lowercase + trimmed for lookup. Registration checks the existing users table by normalized email. (The join_interests table is SEPARATE and must NOT be conflated with users — a join expression-of-interest is not an account.)

PART A — AUTH SERVICE + ENDPOINTS (Express, under /api/auth)
Build an auth service module (testable, framework-light) and these endpoints. All use the unified error envelope established in Join ({success:false,error:{code,message,fields?}}). All rate-limited (extend the existing limiter; per-endpoint buckets; conservative limits — e.g. register 5/hour/IP, login 10/10min/IP with backoff on repeated failure).

- POST /api/auth/register — body: email, password, (optional) displayName. Validate: email format + normalized; password strength (min 12 chars, enforce a documented policy — length + not-obviously-weak; do NOT impose silly composition rules that harm security, follow modern guidance). If email already has a user → return a NON-ENUMERATING response (do not reveal whether an account exists; return a generic success-shaped "if this email can be registered, proceed" OR a neutral conflict — document the chosen non-enumeration strategy). On success: create users row (unverified state — add an is_verified boolean default false to users IF not present, additive nullable/defaulted, report it), create user_credentials row with argon2id hash, create a session, set an HttpOnly Secure SameSite cookie, write auth_events(register + login_success). Do NOT send any email (Module 2.2). Return the safe user representation (id, email, displayName, isVerified) — never the hash.
- POST /api/auth/login — body: email, password. Constant-time-ish failure (same response time/shape whether user missing or password wrong — mitigate user enumeration and timing). On success: create session, set cookie, auth_events(login_success). On failure: auth_events(login_failure), generic error. Apply progressive rate limiting / lockout policy (document it).
- POST /api/auth/logout — requires session; revoke current session (set revoked_at), clear cookie, auth_events(logout).
- GET /api/auth/me — requires valid session; returns the safe current-user representation, or 401 if no/invalid/expired/revoked session. This is the endpoint the frontend uses to know who is logged in.

SESSION MIDDLEWARE
Build Express middleware that: reads the session cookie, hashes it, looks up a non-revoked non-expired session, loads the user, attaches req.user (safe shape) + req.session. Updates last_seen_at (throttled). Rejects cleanly (401, unified error) when absent/invalid. This middleware is the seam the whole authenticated API will use. Sessions expire (documented duration, e.g. 30 days sliding or absolute — choose and document); expired/revoked sessions are treated as logged-out.

COOKIE SECURITY
HttpOnly, Secure, SameSite=Lax (or Strict where it doesn't break flows — document), path=/, appropriate max-age matching session expiry. The cookie contains only the opaque token; all state is server-side.
