PART E1 — POST /api/join-interest
Accepts: fullName, email, country, joiningAs, audienceGroup, category, consentAccepted (required) · organizationName, contactRole (required when joiningAs=organization) · city, sectorSlugs (max 3), programSlugs, notifyOpportunities, lookingFor (max 300 chars) (optional).
VALIDATION (in order, unified error shape on failure): trim all strings → normalize email to lowercase → maximum lengths enforced and published for EVERY string field (conservative: fullName 120, email 254, country 90, city 90, organizationName 160, contactRole 120, lookingFor 300, audienceGroup/category 60) → email format valid → consentAccepted === true → joiningAs ∈ {individual, organization} → audienceGroup ∈ JOINABLE_GROUPS → category ∈ CATEGORIES_BY_GROUP[audienceGroup] (category-not-in-group is a distinct field error) → sectorSlugs: array of strings, no duplicates, ≤3, every slug ∈ SECTOR_SLUGS → programSlugs: array of strings, no duplicates, every slug ∈ PROGRAM_SLUGS → organization conditional fields present when required → unknown top-level fields STRIPPED (documented behavior) → malformed payloads rejected. Reject non-string array members.
DUPLICATE BEHAVIOR (atomic upsert on email_normalized — use Drizzle conflict handling or a transaction; no race-condition duplicates): no existing record → INSERT, status pending, consent_text_version stored → HTTP 201 {"success":true,"submissionId":"<id>","status":"received","message":"Your expression of interest has been received."} · existing record with status pending or reviewed → UPDATE same id with newest valid data (status UNCHANGED: pending stays pending, reviewed stays reviewed), updated_at advances → HTTP 200 {"success":true,"submissionId":"<same id>","status":"updated","message":"Your expression of interest has been updated."} · existing record with status converted → NO modification; return the SAME deterministic response shape as an update (HTTP 200, status "updated", same message) WITHOUT changing the record and WITHOUT revealing account existence — document this exact behavior in the contract · archived → treat as converted-style safe response (do NOT implement archived-restore in Stage 1; document). Never create a second row for the same normalized email. Response never includes stored personal data beyond submissionId.

PART E2 — POST /api/institutional-inquiry
Accepts: organizationName, organizationType, country, contactName, contactRole, email, message, consentAccepted (required) · city, website (optional).
VALIDATION: trim → normalize email → lengths published (organizationName 160, organizationType 60, country 90, city 90, website 200, contactName 120, contactRole 120, email 254, message 1000) → email valid → consent true → organizationType ∈ ORGANIZATION_TYPES → website, if present, must be a safe http(s) URL (reject javascript:, data:, and malformed URLs) → no file uploads, no sensitive-data fields → unknown fields stripped.
DUPLICATES: repeated inquiries from the same email are ALLOWED. Anti-abuse: same-email cap of 3 ACCEPTED inquiries per CALENDAR UTC day (document this model explicitly; normalize email before the cap query; count via created_at within current UTC date). Cap exceeded → HTTP 429 unified error, generic message, never disclosing prior-inquiry count. Success → HTTP 201 {"success":true,"submissionId":"<id>","status":"received","message":"Your inquiry has been received."}
