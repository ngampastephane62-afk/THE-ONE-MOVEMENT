PROJECT CONTEXT
THE ONE MOVEMENT INTERNATIONAL — Tropik Agence FZE LLC. Current Drizzle setup uses drizzle-kit push --force to apply schema changes directly to the live database, bypassing migration files. This has left no auditable schema history — unacceptable given the platform stores personal data under UAE PDPL and (for EU/UK visitors) GDPR. Stage 1.1 checkpoint (Join Stage 1.1 Interest Architecture Complete) stands: the primary_sector_slug column was additive and nullable, all data preserved, tests passed.

This task establishes a documented migration-based workflow WITHOUT changing any application feature, table, column, index, or row. Zero functional change. Zero data disturbance.

STEP 3 — GENERATE THE BASELINE MIGRATION
Configure Drizzle Kit to emit migration files to lib/db/drizzle/ (or the standard location per current Drizzle Kit conventions — verify against the installed version, do not assume). Ensure drizzle.config.ts contains an "out" path pointing to that directory.

Run drizzle-kit generate to produce a baseline migration that represents the current schema state exactly, including primary_sector_slug on join_interests. The generated SQL must describe the current schema; commit it as the baseline. Report the filename and full SQL of the generated file. Under no circumstances hand-edit the SQL to force behavior — if the generator produces destructive statements (DROP TABLE, DROP COLUMN, TRUNCATE, RENAME on existing tables) the task STOPS: report the finding, do not apply, do not force.

STEP 4 — RECONCILE THE JOURNAL WITH THE LIVE DATABASE (non-destructive)
The critical safety step. The live database already contains all tables — running "migrate" naively would attempt to recreate them and fail or corrupt. The correct behavior: mark the baseline migration as ALREADY APPLIED in the __drizzle_migrations journal without executing its SQL, so future migrations proceed cleanly from this baseline.

Implementation options (choose based on the installed Drizzle Kit version — report which):
(a) If Drizzle Kit exposes a supported "baseline" or "mark applied" command in this version, use it.
(b) Otherwise, run a small, documented, one-time SQL statement that inserts the baseline record into __drizzle_migrations (creating the journal table via Drizzle's own initialization if it does not exist) using the exact hash/name conventions Drizzle Kit expects. This SQL must be reviewable and reproducible; include it verbatim in the report.

DO NOT drop, recreate, or alter any existing table or column. DO NOT run drizzle-kit migrate against a database that would treat the baseline as a fresh install. If the reconciliation cannot be performed safely in this Drizzle Kit version, STOP and report — do not force.

STEP 5 — WORKFLOW SCRIPTS
In lib/db/package.json, establish the standard scripts (adjust names to match existing conventions if similar scripts exist — do not create parallel duplicates):
- db:generate — drizzle-kit generate
- db:migrate — drizzle-kit migrate (safe forward-only apply)
- db:status — drizzle-kit status (if supported by this version; otherwise a small script that queries __drizzle_migrations and prints applied migrations)
- db:studio — drizzle-kit studio (if already present; do not add if not)

DEPRECATE push:
- Remove any script alias that invokes "drizzle-kit push --force"
- If drizzle-kit push must remain for local prototyping, gate it behind a script named db:push:local-only-DANGEROUS with a bash-echo warning prefix that prints a red-flag notice explaining it must never be used against shared or production databases
